# Consolidated review gate: CI + PR-comments validation, full result posted to PR and issue (v1)

This change turns code review into a single gate that must be green on three axes before a PR auto-merges: reviewer approval, resolved PR comments, and a green pipeline. `ReviewerResult` grows two fields (`ci_green`, `unresolved_comments`) and its `is_auto_mergeable` now folds them in; the domain `decide()` additionally takes an injected `pr_ci_green` so a freshly-observed red pipeline blocks `MERGE_PR` and escalates to the TL even when the stored result looks clean. The deployment layer computes `pr_ci_green` via a new `gh statusCheckRollup` read reduced to green/red/pending/none, and both the auto-merge and change-requested paths now post the *complete* result to the PR and to the issue (not just a short reference). The reviewer prompt is rewritten to make CI and comment-resolution checks explicit preconditions for `crewflow:reviewed`.

Watch for: (1) `pending` CI is collapsed into the same `False` that red produces, so the block reason text and the reviewer's log always say "vermelha" even when the pipeline is merely still running — **confirmed**, minor but user-visible. (2) The fresh CI re-check has no equivalent for unresolved comments — comment freshness is trusted entirely from the stored `ReviewerResult`, an asymmetry the injected `pr_ci_green` was introduced to avoid for CI — **confirmed**. (3) The complete-result post to the issue uses `add_issue_comment` (append), not the idempotent state-comment upsert, so re-processing an issue can duplicate the full block — **likely**, bounded by existing anti-spam on the TL path.

**Verdict**: APPROVED

## High-level view

The gate is enforced in two layers that reinforce each other. `ReviewerResult.is_auto_mergeable` encodes the static contract (approved, zero change requests, `ci_green is not False`, zero unresolved comments), and `decide()` adds a live guard using the injected `pr_ci_green`, so a red or pending pipeline observed at decision time blocks the merge regardless of what the reviewer recorded. `None` is deliberately non-blocking on both the stored `ci_green` and the injected `pr_ci_green`, which is what preserves legacy results and Jira (no CI) — the same tolerance already applied to a missing SHA.

Domain purity is intact: CI status is fetched by the deployment adapter (`_check_pr_ci` → `get_pr_ci_status` → `get_pr_checks_status`) and passed into `decide()` as a plain `bool | None`, mirroring how `pr_head_sha` is already injected. `test_domain_boundary.py` still passes.

Result completeness is achieved by routing both the auto-merge path and the change-requested/NOTIFY_HUMAN path through `_post_reviewer_result_on_pr`, which posts the full render to the PR and then calls `_update_issue_with_pr_ref` to (a) keep the complete `ReviewerResult` in the issue's state comment and (b) post a separate complete-result comment via the new `render_issue_review_result`. The issue no longer receives only a short reference.

The reduction from `statusCheckRollup` is "worst state wins" — any failure/cancel/timeout is red, anything still running is pending, otherwise green, and no checks at all is none. `_check_pr_ci` then maps green→True, red/pending→False, none/error→None and never raises, degrading I/O failure to the non-blocking `None`.

### Two-layer gate: static contract vs live CI guard

`is_auto_mergeable` moved from `approved and len(comments) == 0` to a four-way conjunction that also requires `ci_green is not False` and `len(unresolved_comments) == 0`. The `is not False` (rather than `is True`) is the load-bearing choice: it lets `None` through so a legacy result or a Jira item with no CI concept is not blocked, matching the existing SHA-tolerance convention. `decide()` layers a second, independent check on top — even when `is_auto_mergeable` is True, an injected `pr_ci_green is False` diverts to `NOTIFY_HUMAN` (TL) instead of `MERGE_PR`. The two layers are not redundant: the property reflects what the reviewer *recorded*, the injected value reflects what CI *is right now*, so a pipeline that went red after the reviewer wrote its result is still caught.

```
reviewer_result.is_auto_mergeable ──true──► pr_ci_green is False? ──yes──► NOTIFY_HUMAN (TL)
        │                                          │
        │                                          no ──► MERGE_PR
        └── false ──► changes-requested / NOTIFY_HUMAN
```

The `test_ci_*` cases in `test_executor.py` exercise all three injected values against an approved, comment-free stored result, so reverting the `if pr_ci_green is False` block would flip the red case from `NOTIFY_HUMAN` back to `MERGE_PR` and fail the test — the tests genuinely bind the new path rather than mocking it away.

### CI reduction and the pending-as-red conflation

`get_pr_checks_status` reduces the rollup worst-state-first (red on any failure/cancel/timeout/action-required/stale conclusion or FAILURE/ERROR commit-status state, pending on anything in-progress/queued, else green, none for empty). The `(status and status != "COMPLETED")` catch-all treats unknown check states as pending.

The behavioral wrinkle is downstream: `_check_pr_ci` collapses both `red` and `pending` into `False`, and `decide()`'s escalation reason is the fixed string "reviewer aprovou mas a pipeline (CI) está vermelha". A PR whose CI is still running therefore escalates to the TL with a message asserting the pipeline failed. The `_check_pr_ci` info log distinguishes the two (`pipeline ... = %s`), but that distinction is dropped before it reaches the human-facing reason. Blocking on pending is the intended safety behavior; only the labeling is misleading.

### Result completeness on both paths

Both terminal paths converge on `_post_reviewer_result_on_pr`: the auto-merge path calls it before merging, and the change-requested TL path calls it before notifying (guarded by `sc_obj.reviewer_result is not None`). That function posts the full `render_pr_review_comment` body — now always including the CI label and issue link — to the PR, then delegates to `_update_issue_with_pr_ref`. The rewrite of `_update_issue_with_pr_ref` is where the "issue gets only a short reference" gap is closed: it still keeps the complete `ReviewerResult` in the state comment (what the scan reads for MERGE_PR) and adds the history transition, but now also posts a standalone complete-result comment through the new `render_issue_review_result`, which carries result/reviewer/CI/PR-link/SHA/change-requests/unresolved-comments.

The one caveat is delivery mechanics: the state comment is upserted (idempotent by marker), but the complete-result comment is appended via `add_issue_comment`. On the auto-merge path this runs once before merge, so duplication is unlikely; on the TL path the `awaiting-tl-approval` anti-spam short-circuits re-notification, so the full-result post is not re-emitted on subsequent cycles. The duplication risk is real only if a code path can re-enter `_post_reviewer_result_on_pr` for the same issue without the state having advanced — low today, but the append semantics make it a latent foot-gun worth an upsert-by-marker.

### Domain purity preserved

Both `run()` and `_run_stage()` compute `pr_ci_green` inside the existing REVIEW+REVIEWED block and pass it through the same `decide(...)` call — a gap in either entrypoint would silently disable the CI gate for that path, so their symmetry matters. `test_domain_boundary.py` passes.

### Round-trip and rendering

`_parse_block` grows dedicated `in_unresolved_list` tracking alongside the existing change-requests list so the two bulleted sections don't bleed into each other on parse. `test_roundtrip_*` assert `is_auto_mergeable` on the *reconstructed* object across verde/vermelho/none, so the parsed result — the one the scan actually reads — is checked against the gate, not just the constructed instance.

### Test coverage

The new tests cover the three CI outcomes at the domain layer, the reduction table (green/red/error/pending/none/error-propagation) at the transport layer, the client delegation, both render functions including CI label and issue/PR links, the prompt template's CI+comment instructions, and two deployment integration cases (red blocks merge but still posts to the PR; green merges). The integration red-path test asserts both `merge_pull_request` was not called and `upsert_pr_review_comment` was called, so it binds the "block but still post" behavior.

Not tested: the `pending`→`False` path end-to-end through `_check_pr_ci` and `decide()` (only `red` is exercised at the integration layer, so the misleading "vermelha" reason on pending CI is not asserted either way); the duplicate-comment behavior of `add_issue_comment` across repeated cycles; and `_update_issue_with_pr_ref` posting the complete result to the issue is not directly asserted in the integration tests (the issue-side `add_issue_comment` is patched but not checked for the full-result body).
