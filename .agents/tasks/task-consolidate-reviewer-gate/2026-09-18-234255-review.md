# Pending-vs-red CI labeling and idempotent issue result post (v2)

The v1 review approved the consolidated reviewer gate and flagged three non-blocking issues: pending CI mislabeled as "vermelha", no live re-check for unresolved comments, and the full issue-side result posted via append rather than upsert. Commit `b7b7006` addresses all three. `decide()` now takes an injected tri-state `pr_ci_status` (`'green'|'red'|'pending'|'none'|None`) alongside the still-blocking `pr_ci_green` bool, so the escalation reason distinguishes "pendente (em execução)" from "vermelha" while both continue to block; `_check_pr_ci()` returns `(gate, status)` and both entrypoints thread the status through. The append is replaced by `upsert_issue_review_result()`, a marker-anchored upsert mirroring the existing `upsert_state_comment`. The comment asymmetry is now justified by an inline comment rather than code.

Watch for: nothing blocking. The tri-state stayed a pure label — the domain gains no I/O and blocking is still governed solely by `pr_ci_green is False` (**confirmed**). Pending and red both still divert to NOTIFY_HUMAN/TL, so safety is unchanged (**confirmed**). The issue-side upsert reuses the exact transport calls and 0→create/1→update/N→update-first+delete-extras convention already proven by `upsert_state_comment`, and the last remaining `add_issue_comment` call is the post-merge notification, which fires once and cannot stack (**confirmed**).

**Verdict**: APPROVED

## High-level view

The pending-vs-red fix is a labeling-only change with the block preserved. `_check_pr_ci` still maps both `red` and `pending` to a `False` gate, so the auto-merge is blocked in both cases exactly as before; the second tuple element carries the raw status so `decide()` can pick "pendente (em execução)" vs "vermelha" for the human-facing reason. The gate condition (`pr_ci_green is False`) is untouched, so a missing `pr_ci_status` simply falls through to the "vermelha" default — backward compatible, and `None` still never blocks.

Domain purity holds. `pr_ci_status` is injected into `decide()` alongside `pr_ci_green`, computed by the deployment adapter and passed as a plain string; the executor module still imports nothing beyond stdlib. Both `run()` and `_run_stage()` unpack `_check_pr_ci`'s new tuple and forward the status, so the two entrypoints stay symmetric — a gap in either would have desynced the label from the gate.

The issue-side full result is now idempotent. `render_issue_review_result` prefixes the body with the new `ISSUE_REVIEW_RESULT_MARKER`, and `upsert_issue_review_result` anchors on that marker using the same get/create/update/delete transport primitives and the same "update the first, delete the extras" convention as `upsert_state_comment`. `_update_issue_with_pr_ref` calls the upsert instead of appending, so re-processing the same issue overwrites in place rather than stacking duplicate full-result blocks.

The unresolved-comments asymmetry is documented, not re-engineered. An inline comment in `decide()` explains that CI gets a live re-check because it can turn red after the reviewer wrote its result, whereas comment resolution is treated as authoritative from the stored `ReviewerResult` and a live thread re-fetch is deliberately out of scope. The reasoning is coherent and matches the actual code path.

### Pending vs red: label split without weakening the block

`_check_pr_ci` now returns `(bool | None, str | None)`: `green→(True,'green')`, `red→(False,'red')`, `pending→(False,'pending')`, and `none`/error→`(None, status)` (I/O failure degrades to `(None, None)`). The gate element is identical to v1 — pending is still `False`, so it still blocks — and only the second element is new. `decide()` reads it purely for wording: inside the existing `if pr_ci_green is False` branch it selects "a pipeline (CI) ainda está pendente (em execução)" when `pr_ci_status == "pending"` and "a pipeline (CI) está vermelha" otherwise. Any non-"pending" value, including `None`, produces the "vermelha" default, which is what preserves the legacy call shape where no status is supplied.

`test_ci_pendente_bloqueia_merge_mas_rotula_pendente` binds the fix: it asserts `NOTIFY_HUMAN` + TL (block preserved) and that the reason contains "pendente" but not "vermelha". `test_ci_vermelha_...` asserts the inverse, and `test_ci_vermelha_sem_status_mantem_rotulo_vermelha` pins the no-status backward-compat default. These would fail if the branch reverted to the hard-coded string, so they genuinely bind the behavior rather than mocking it.

### Idempotent issue-side result

```
render_issue_review_result ──prefixes──► ISSUE_REVIEW_RESULT_MARKER
                                              │
_update_issue_with_pr_ref ──► upsert_issue_review_result(repo, issue_number, body)
                                              │
     get_issue_comments ─► filter by marker ─┼─ 0 → create_issue_comment
                                              ├─ 1 → update_issue_comment(first)
                                              └─ N → update first + delete_issue_comment(rest)
```

`upsert_issue_review_result` is a line-for-line structural match to `upsert_state_comment` on a different marker, using the same four transport functions (`get_issue_comments`, `create_issue_comment`, `update_issue_comment`, `delete_issue_comment`), all of which exist. It passes `issue_number` as an int straight through, matching the pre-polish `add_issue_comment` contract it replaces (the state-comment path uses `str()`+`_parse_issue_number` because its key can be a URL; the issue-result path always receives the numeric id from `_update_issue_with_pr_ref`). The dedup arm restores the single-comment invariant even for issues that accumulated appends under the old code path.

`TestUpsertIssueReviewResult` covers create, update-in-place, no-duplicate-create, an N-call idempotency loop that asserts exactly one marker comment survives with the latest body, and a dedup case asserting the first is updated and ids 20/30 are deleted. The deployment integration test `test_ci_pendente_nao_mergeia_e_upserta_resultado_na_issue` closes the v1 gap end-to-end: it asserts `merge` not called, PR post made, `upsert_issue_review_result` called with the marker in the body, and `add_issue_comment` **not** called — so it binds both the pending-blocks and the append→upsert switch on the real `run()` path.

### Unresolved-comments asymmetry documented

The inline comment in `decide()` states the trade-off: CI gets a live re-check via injected `pr_ci_green` because a pipeline can go red after the review was written, while unresolved comments are trusted from the stored `ReviewerResult` since the reviewer is the authoritative source and a live thread re-fetch would add I/O and parsing without comparable safety gain. The reasoning matches the code — there is no live comment re-fetch, and the gate on `unresolved_comments` remains inside `is_auto_mergeable`. This resolves the v1 concern as an explicit, justified design decision.

### Regression check against v1-approved behavior

Green still merges (`pr_ci_green is True`/`None` never enters the block), red still blocks with the "vermelha" reason, `None` remains the legacy/Jira-tolerant non-blocking value on both the stored `ci_green` and the injected gate, and the complete result still reaches both the PR (`upsert_pr_review_comment`) and the issue (now via upsert). Domain boundary test passes. Full suite: 530 passed, 1 failure — `test_template_corrompido_ilegivel_usa_fallback`, which is the known root-only `chmod 0o000` bypass unrelated to this change and failing on baseline too. Not a regression.
