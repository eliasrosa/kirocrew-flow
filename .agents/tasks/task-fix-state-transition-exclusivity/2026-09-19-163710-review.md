# Atomic state-label transition to enforce "one crewflow state per issue"

Introduces `transition_state(labels, novo_estado)` in the domain layer as the single source of truth for a state change: it returns a label set with exactly one `crewflow:` state, dropping every other state while preserving modifiers, type/priority, and foreign labels. The driving adapter (`deployment.py`) routes state changes through it — a new `_apply_dev_transition` fires a deterministic `todo→dev` via `provider.set_labels` right after a dev dispatch, and `_apply_decision_labels` centralizes rebrand / needs-human / mark-conflito / auto-merge label writes with the same exclusivity guarantee. The `dev.md` prompt is also updated to tell the one-shot agent to remove prior states in the same `gh` operation. The change is a direct response to issue #107, where an issue carried both `crewflow:todo` and `crewflow:review` and stalled the reviewer dispatch.

Watch for: the `dev→review` transition — the exact one that produced the #107 accumulation — is still applied only by the LLM session following the prompt; the engine never removes the prior state on the review path (confirmed). The deterministic engine-side fix covers `todo→dev` only. Everything else (domain helper correctness, guard placement, modifier-only routing, test quality) checks out.

**Verdict**: NEEDS_CHANGES

## High-level view

The domain helper is the right shape: pure, no I/O, idempotent, accepts `set`/`frozenset`/`list`, and collapses any number of pre-existing states down to one. It genuinely preserves modifiers, type/priority, and foreign labels.

The engine-side fix is deterministic for `todo→dev` only. `_apply_dev_transition` runs on the committed-dispatch path (inside the `try` after `_dispatch` succeeds), so it respects `auto_dispatch`, `vagas`, the per-issue active-session guard, and headroom — no double-dispatch, no firing under dry-run. It is applied identically in both `run()` and `_run_stage`.

The `dev→review` transition is not enforced by the engine. The reviewer dispatch path in `run()` only calls `_dispatch_reviewer` and the `DISPATCH_REVIEWER` decision adds the `reviewed` modifier — no state label is rewritten. Moving out of `todo`/`dev` into `review` still depends on the one-shot agent obeying the updated `dev.md` prompt. That is the same LLM-driven mechanism whose failure caused #107; the fix hardens the `todo` side of that transition but not the `review` side.

`_apply_decision_labels` correctly distinguishes a state add from a modifier-only add: a `crewflow:conflito` decision leaves the current state untouched, while a decision carrying a state label routes through `transition_state`. The auto-merge path composes `add=done` / `remove=reviewed` through the same helper, so `review→done` drops `review` cleanly.

The new tests are revert-sensitive and would fail if the helper or the wiring were removed. The one gap is that no test exercises the `dev→review` transition through a real engine path — the closest test calls `transition_state` directly, which does not prove the engine ever invokes it on that path (because it doesn't).

<summary>Details</summary>

### `todo→dev` is deterministic and correctly gated

`_apply_dev_transition` sits inside the dispatch `try`, after `_dispatch` returns, so it only fires for a dispatch that actually happened. The surrounding loop already enforces `auto`, `vagas <= 0`, `_issue_has_active_session`, and `_resource_headroom_ok` before reaching it, and dry-run never enters this loop. Both the monolithic `run()` and the per-stage `_run_stage` apply it identically. Failures are logged and swallowed: the dispatch already fired, so raising would only strand the loop, and the next scan cycle re-observes the label state.

```
run() dispatch loop
  guards: auto? vagas? active-session? headroom?
    _dispatch(...)              ← session fired
    _apply_dev_transition(...)  ← set_labels(dev + running, todo removed)
```

### The review path still leans on the prompt

This is the load-bearing concern. The bug in #107 was an issue stuck with `todo` **and** `review`. The engine-side fix removes `todo` when entering `dev`, but the transition into `review` is where the accumulation actually manifested, and that transition is not owned by the engine. In `run()`, the `dispatch_reviewers` loop calls `_dispatch_reviewer` and nothing else touches state labels; the `DISPATCH_REVIEWER` decision contributes `crewflow:reviewed`, a modifier, not a state. The state move `dev→review` happens only when the one-shot dev agent opens the PR and runs the `gh issue edit ... --add-label crewflow:review --remove-label crewflow:dev --remove-label crewflow:todo` that the prompt now spells out.

So the reliability of the review transition still rests on the model following instructions — the same failure mode that produced #107. Hardening it (an engine-side `review` collapse on PR-open, mirroring `_apply_dev_transition`) would close the loop the bug report actually describes.

### Test quality

The domain suite covers the collapse of two simultaneous states to one, modifier/type/priority/foreign-label preservation, idempotency, no-input-mutation, and every target state. The e2e suite drives `_apply_decision_labels` (two-state #107 reproduction and the conflito modifier-only case), `_apply_dev_transition` in isolation, and a full `run()` with `auto_dispatch` asserting `set_labels` is called once with `dev` present, `todo` absent, and type/priority preserved. These fail on revert — the helper and adapter functions wouldn't exist, and the `run()` test would see `set_labels` uncalled.

Not tested: the `dev→review` transition through any engine path. `test_transition_state_review_derruba_dev` calls `transition_state` directly, which proves the helper works but not that the engine ever calls it on the review path — and it currently doesn't.
