# Engine-side enforcement of `crewflow:review` exclusivity (v2)

Follow-up to the v1 review, which returned NEEDS_CHANGES because the `dev→review` transition — the exact move that produced the #107 accumulation — was still applied only by the one-shot LLM session, never by the engine. This pass adds a pure `state_labels_present()` domain helper (reports every state label without raising, unlike `parse_state`), a `_apply_review_transition()` that collapses an issue to exactly `crewflow:review` before reviewer dispatch, and a defensive `_enforce_review_exclusivity()` pre-pass that reconciles the ambiguous two-state issues the scanner discards. Four new engine-path tests drive `run()` and assert the engine itself rewrites the labels. The dual-writer for `todo→dev` (v1 Issue 2) was intentionally kept as belt-and-suspenders.

Watch for: the load-bearing fix for the actual #107 failure is the pre-pass, not the dispatch-loop call — an ambiguous `todo`+`review` issue never reaches `dispatch_reviewers` because the scanner drops it, so `_apply_review_transition` on that loop is a guaranteed no-op for issues that got there (confirmed, not a bug, but the reviewer should understand where the real coverage lives). Minor: a dead `if … pass` branch in `_apply_review_transition` (confirmed) and an unconditional per-cycle `list_by_state` API call in the pre-pass (confirmed, low cost). All three v1 concerns are resolved or consciously accepted.

**Verdict**: APPROVED

## High-level view

`state_labels_present()` is the right primitive: pure, no I/O, never raises, accepts `set`/`frozenset`/`list`, returns the full set of state labels so the deployment layer can *detect* accumulation without inheriting `parse_state`'s `EstadoAmbiguo` throw. It reuses the existing `transition_state()` for the actual collapse.

The engine now enforces `→review` on two paths. `_apply_review_transition()` runs in both reviewer-dispatch loops (`run()` and `_run_stage`) right before `_dispatch_reviewer`, and is idempotent — it skips `set_labels` when the issue already carries exactly `crewflow:review`. But an issue only reaches those loops after the scanner parsed it as a single clean `review` state, so on that path the call is effectively always a no-op. The transition that actually rescued #107 is `_enforce_review_exclusivity()`.

`_enforce_review_exclusivity()` is the real fix and it targets the precise failure mode: a two-state issue (`todo`+`review`) is ambiguous, so `parse_state` raises, the scanner sets `current_state=None` and drops it, and it never appears in `scan_results` — which is exactly how #107 stalled. The pre-pass sidesteps the scanner entirely, lists issues by the `crewflow:review` label straight from the provider (which matches regardless of other labels present), and collapses any that still carry a second state. It runs before the "nothing to do" early-return and is gated by `not dry_run` in `run()` and additionally by `stage == _STAGE_REVIEWER` in `_run_stage`.

The new tests are genuinely engine-path: two of the four call `run()` and assert the engine — not the domain helper — invokes `set_labels` with exactly `crewflow:review`. Disabling the two enforcement call sites makes those two tests fail, so they are revert-sensitive. The ambiguous-#107 reconciliation test drives an empty `scan_results` and proves the pre-pass acts on an issue the scanner discarded.

Two cosmetic residuals remain: a no-op `if … pass` block inside `_apply_review_transition` and an unconditional `list_by_state` call each cycle. Neither affects correctness.

### Where the #107 fix actually lives

The v1 review flagged that the engine only hardened the `todo` side of the transition. This pass closes it, but the coverage is asymmetric between the two new call sites and it's worth being precise about which one matters.

`_apply_review_transition` sits in the reviewer-dispatch loop, after `_reviewer_has_active` and immediately before `_dispatch_reviewer`. An issue reaches that loop only via a `DISPATCH_REVIEWER` decision, which the scanner emits only after `parse_state` succeeded — and `parse_state` raises on two states. So any issue in `dispatch_reviewers` already has exactly one state (`review`), which means `state_labels_present` returns `{crewflow:review}` and the function returns `False` without writing. It is a correct, idempotent guard, but for the #107 scenario it is structurally a no-op: the corrupted issue never gets that far.

`_enforce_review_exclusivity` is what recovers the stalled issue. It bypasses the scanner and queries the provider directly:

```
run()  ──►  _enforce_review_exclusivity(provider, repos, projects)   ← BEFORE early-return, not dry_run
                │
                ├─ provider.list_by_state(project, "crewflow:review")  ← matches label regardless of other states
                │
                └─ for each issue with 2+ states:
                       transition_state(labels, REVIEW) ─► set_labels(exactly crewflow:review)
```

Because the label query matches on the `crewflow:review` label independent of the co-present `crewflow:todo`, it sees exactly the issue the scanner threw away. This is the deterministic engine-side path the bug report asked for, and it runs before the "nothing to do" early-return so an otherwise-idle cycle still reconciles.

### Placement, dry-run, and duplicate-write analysis

In `run()`, the pre-pass is at the correct point: after dead-session candidate collection, before `_log_cycle_summary` and the `if not any([...]): return` early-return, guarded by `if not dry_run`. `_run_stage` mirrors it with the extra `stage == _STAGE_REVIEWER` guard so the dev stage doesn't waste an API call reconciling review issues. Dry-run never writes: the top-level `dry_run` short-circuits are upstream, and both enforcement sites are explicitly gated.

There is no duplicate `set_labels` within a cycle. The ambiguous issue handled by the pre-pass is absent from `scan_results`, so it never reaches the dispatch loop's `_apply_review_transition`; a clean single-state issue that does reach the loop is a no-op in both places. The pre-pass also dedups within its own run via a `seen` set keyed on issue key, so the same issue listed under multiple projects is collapsed once.

The `repo` derivation inside the pre-pass (`key.split("/issues/")[0].replace("https://github.com/", "")` with a fallback to `repos[0]`/`project`) matches the convention used everywhere else in the module for reconstructing a repo slug from a canonical key.

### The dead branch in `_apply_review_transition`

One non-obvious side effect worth noting: on collapse the function updates `issue["_labels"]` in place, so a later reader in the same cycle sees the reconciled set rather than the stale one.

The blemish is the middle branch:

```python
if State.REVIEW.value not in present and len(present) <= 1:
    pass
```

It evaluates a condition and does nothing, then unconditionally proceeds to `transition_state(base_labels, State.REVIEW)`. The comment explains the intent (an issue being treated as review by dispatch should still collapse to one state), but the code expresses that by *not* branching at all. Removing the block changes no behavior and makes the "everything that isn't already exactly `{review}` collapses to review" contract obvious.

### Tests exercise the engine, not just the helper

The v1 gap was that the review-collapse test called `transition_state` directly. That's fixed. `test_run_dispatch_reviewer_colapsa_estado_residual` and `test_run_enforce_review_exclusivity_reconcilia_107_ambigua` both call `run()` with mocked provider/scanner and assert the engine drives `set_labels` to exactly `{crewflow:review}` with `feature`/`p1` preserved. The ambiguous test is the strongest: `scan_candidates` returns `[]` (the scanner dropped the issue), yet `set_labels` is still called once with the collapsed set — proving the pre-pass, not the dispatch loop, did the work. Disabling both enforcement call sites in `deployment.py` makes exactly these two tests fail with `set_labels … Called 0 times`, confirming revert-sensitivity. The two unit-level tests (`_apply_review_transition` collapse and idempotence) round out the direct coverage.

Not tested: `_enforce_review_exclusivity` when `list_by_state` raises (the swallow-and-continue path) and the multi-project dedup via the `seen` set. Both are defensive branches; their absence is low-risk but they are untested.

### Acceptance criteria

Applying a state removes every other state (`transition_state`, unchanged and reused). Modifiers and type/priority are preserved (helper + tests). No issue ends with 2+ state labels once a reviewer cycle runs — the pre-pass now reconciles the ambiguous case that previously stalled, which is the concrete #107 scenario. The `todo→dev→review` accumulation is covered by an engine-path test. README/steering reinforcement landed in the earlier commits. All five criteria are met.
